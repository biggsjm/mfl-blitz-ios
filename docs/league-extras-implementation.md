## Navigation and interaction

The five tabs and six My Team shortcuts are unchanged. Trades adds Offers / Trading Block, defaulting to Offers. Schedule adds Matchups / Calendar, defaulting to Matchups. Once visited, each mode remains mounted to preserve its scroll position; hidden modes are not interactive or exposed to accessibility. New feeds do not join startup loading.

Trading Block has a visible Add/Edit/Resume action, owner/team identity, player/pick listings and Make offer. Build 34's editor follows Lineup: On the block above Your roster, green up/orange down controls, position badges and a pinned Review & submit trading block action. Owned draft picks are secondary. A separate review lists every intended asset and needs text, offers Cancel, and requires a final Submit trading block. Neither moving a row nor canceling review changes the roster, lineup or published listing. Prefilling an offer never sends it and never silently replaces an existing offer draft. Block drafts are separate from trade-offer drafts. Close prompts after changes; blank new drafts, unchanged listings and overlong publication notes cannot submit. Build 35 distinguishes an empty existing listing: Review removal → Remove listing explicitly clears the listing and needs note, never the roster or lineup. This removal draft can be saved/resumed; canceling review retains it. A saved draft can be explicitly discarded without changing the published listing. Offering new FAAB dollars stays on MFL.

Build 34 moves the Settings gear from Scores to the upper-left of My Team. Scores retains its trailing Week control. The Live Activity preference is therefore My Team → Settings → Game day.

Calendar is a dated agenda grouped as Today, This week and Later, with Earlier events collapsed. Event details distinguish waiver processing from availability windows and trade deadlines. Navigation to bids/players/trades does not submit anything or change the edited lineup week. Date/source information uses an anchored information popover. Unknown or incomplete recurrence is disclosed instead of becoming a precise inferred deadline.

## API and data contracts

- `tradeBait` export: `INCLUDE_DRAFT_PICKS=1`; five-minute ordinary memory cache. Josh supplied the empty `tradeBaits:{}` and camel-case singleton `tradeBaits.tradeBait` response, with `franchise_id`, `willGiveUp`, `inExchangeFor`, `timestamp`. Tests use fictional assets/text. Player/current/future pick codes reuse existing trade asset parsing; recognized legacy cash codes can be displayed, not newly published.
- `tradeBait` import: owner-only full replacement, one POST with `WILL_GIVE_UP` and `IN_EXCHANGE_FOR` (maximum 256 characters). Fresh account membership, authoritative block/assets and exact owner abilities precede publication. An existing listing changed elsewhere stops the write. Unsupported current assets cannot be silently removed. A durable scoped pending marker precedes POST; full terms readback clears it. Timeout/cancellation/error never triggers an automatic retry. Check status is read-only. An unresolved marker intentionally blocks another publication; check MFL before disconnecting/reconnecting to clear local recovery state.
- Build 35 removal uses a separate core entry point with **both fields explicitly present and empty**. This follows the documented full-replacement form; MFL does not explicitly describe empty-list behavior, so live server acceptance is not claimed from fixtures. Removal requires an existing matching baseline, fresh exact owner membership and TRADES permission, a durable empty intended-list marker and one POST. Only a successfully parsed fresh export that omits the owner or contains an empty asset set **and** empty needs text confirms removal. Unchanged data, failed reads or timeouts retain recovery state without replay. Explicit full removal may clear unsupported old assets; an ordinary partial edit still cannot silently discard them.
- Calendar JSON: one 15-minute cache shared with waiver timing. `id`, `type`, `title`, `start_time`, `end_time`, `happens` are parsed strictly; bad data cannot become an empty calendar. An additional shared/cached ICS read occurs only for repeated series.
- ICS: the supplied MFL file expands each repeated series into explicit events. All JSON anchors must match the ICS UID and UTC clock representation; the feed omits a zone suffix, so the app never treats it as device-local floating time. November's one-hour shift comes from MFL's published occurrences, not app-generated weekly arithmetic. Repeated series require an unambiguous summary mapping, the expected additional count and complete coverage. Other ICS schemas, RRULEs, all-day dates, TZID variants or exclusions are deliberately not guessed.
- Reminder identity uses the JSON series ID plus occurrence index, scoped to season/league/franchise, not the generated ICS child UID. A moved date replaces the same reminder. The complete/partial flag matters: only a successfully verified complete feed can remove absent future events wholesale; a failed/partial feed preserves existing reminders.
- Calendar and block snapshots retain original fetch dates in bounded, unlocked-device-only Keychain storage (maximum 1 MB each, seven-day display age). Actor-owned I/O is off the UI thread. Display caches confer no publication permission. Cancellation does not empty a snapshot. Ordinary reads coalesce; explicit verification waits for an older read then starts a fresh one.

## Deadline reminders

Notifications are off until the user chooses an event or category. Timing choices are 15 minutes, one hour (default), and one day before. Enable stays visible in the sheet's confirmation toolbar, not below the scrollable options. Event overrides take priority over category preferences. Past triggers are disabled; the app never schedules a late catch-up alert. Fresh calendar verification precedes enabling, followed by contextual iOS permission. Denial offers iOS Settings, not repeated permission prompts.

The planner schedules at most 32 pending app reminders within the next 14 days. Stable hashed identifiers prevent duplicates; per-event changes replace existing requests. Complete successful refreshes remove obsolete requests; failed refreshes are not deletions. Opting out cancels matching reminders, including while offline. Requests use absolute dates, not repeating weekly notification triggers. Alerts contain short event-type/date text and an opaque scoped navigation URL, not bid amounts, trade terms, credentials or custom private descriptions.

Scheduled local alerts can arrive while Blitz is closed, subject to iOS permissions/Focus/delivery. Changes made by a commissioner while the app is suspended cannot be learned until a later refresh. Foreground entry reconciles only when reminders are enabled; no launch-time permission prompt or new unconditional network stream is added. Disconnect stops new scheduling, drains in-flight work, cancels this app's requests and clears the team's reminder settings/cache.

Selected-event Apple Calendar handoff uses `EKEventEditViewController`; the user reviews and saves. Blitz neither reads the user's calendars nor requests full calendar access. This is a one-time copy, not synchronization or guaranteed duplicate detection. The editor's resulting save is not inspected. Offline Preview disables personal-calendar insertion and uses a notification service that never asks iOS for permission or schedules real alerts.

## Matchup Live Activity

The new WidgetKit extension provides Lock Screen and compact/minimal/expanded Dynamic Island presentations. It shows team names, scores, active-starter count and update time. A single positively identified owner matchup in the confirmed current week is required; active bench players alone do not qualify. Missing clocks, pregame, old weeks, stale snapshots and cached/unverified sessions do not start an activity. No fake kickoff-time inference is used.

It updates from the existing foreground score path. When another tab/week is open, a bounded foreground read can reuse the shared score cache without changing that tab/week. The activity's content becomes stale after two minutes and then says Update needed / Open Blitz to update, including a clock indicator in compact/minimal views. It ends after fresh data shows no active matchup starters, on disconnect, or when disabled. User dismissal is remembered for that matchup/week; re-enabling in Settings can resume it. The app adopts matching activities after relaunch and handles system-ended activities.

There is **no APNs backend, background polling guarantee, push-to-start token or server credential storage**. ActivityKit's extension cannot itself fetch network data. Scores refresh while Blitz is running in the foreground; the widget explicitly represents older data afterward. iOS may end an activity after its lifecycle limit. Continuous background sports updates are a separate future service decision, not silently implemented with an unreliable background timer. Tapping the activity opens a scoped matchup in its own navigation sheet and preserves lineup drafts/selected weeks.
